# Labor Hours and Jobs production runbook

This is the October 13, 2026 integration runbook. Production remains untouched; development uses separate verification data. The development history remains in [labor-development.md](labor-development.md). The release includes job-by-job manager review, immutable approval and an explicit Housecall send path. **Live labor sending remains disabled and no labor hours or costs have been sent.** Internal job linking and approval never dispatch writes. Existing receipt approval/export behavior remains unchanged.

## Release gates and existing accounts

The production pages and APIs require `LABOR_ENABLED=1`. Keep that flag off until the database migrations, source-file transfer, access checks, and worker acceptance pass. Production always uses Supabase persistence; a missing database is an error rather than a local-file fallback. A preview should use its own development database, credentials, worker token, and session key.

Reuse the receipt application's existing Supabase Auth users and profile roles. Do not copy users, passwords, or sessions from the local preview. Existing active managers/admins access Labor Hours and Jobs through the same login and authorization as the receipt inbox. Workers remain in the field app; anonymous, worker, and disabled accounts must fail the labor manager checks. Original-workbook downloads use authorized application endpoints. The private workbook and encrypted worker-session buckets are not public or available through ordinary authenticated Storage access.

`LABOR_LOCAL_PREVIEW=1` is only an explicitly enabled loopback development preview with filesystem persistence. It must remain off in preview/production. Browser mutations require the application's existing same-origin or authenticated request checks. Worker endpoints have a separate server-only token and narrowly scoped lease/session contracts; they do not grant manager access or receipt approval.

## Database and private originals

Commit and apply all six repository migrations in this order:

1. `supabase/migrations/20261013180457_labor_shared_persistence.sql`: shared state, per-import source records, immutable control-change audit, private original/session buckets, compare-and-swap updates, and all-bucket Storage monitoring.
2. `supabase/migrations/20261013182239_labor_worker_session_lease_fence.sql`: prevents an expired worker lease from replacing the encrypted session after a newer connection.
3. `supabase/migrations/20261013183059_labor_worker_session_expiry_after_locks.sql`: checks natural lease expiry after acquiring both the labor-control and session locks, so lock waits cannot extend authorization for a stale session write.
4. `supabase/migrations/20261013184807_labor_import_commit_lease_fence.sql`: validates the worker lease, command and import period at the atomic import commit after acquiring the shared ledger row lock, so a lease that expires during a lock wait cannot activate imported reports.
5. `supabase/migrations/20261013220712_labor_job_hour_approval_ledger.sql`: immutable job-hour/cost approval snapshots, source-interval reservations across replacement imports and job remaps, audited manual-send claims, dispatch leases and verification-only uncertain outcomes. It creates no business approvals or provider writes.
6. `supabase/migrations/20261013223737_labor_job_hour_point_precision.sql`: retains minute-rounded positive source points and conservative cross-approval duplicate checks without modifying original clocks or quantities. Zero-hour source rows remain evidence rather than approved intervals.

The worker download guard, structured parser and private original bucket have a separate 10 MiB file ceiling, which does not increase the HTTP import allowance. Split acquisition into smaller permitted date ranges when necessary; do not raise limits in deployment configuration without reviewing memory and host request capacity.

## Manager approval and Housecall labor costs

In **Jobs**, select a linked Housecall job and review its work-date range. All workers are included initially; a manager can explicitly choose a worker subset. Missing-rate time must be priced or explicitly left outside that approval; owner time is never silently assigned a zero rate. The review includes original quantities/clocks and source rows, daily worker totals, paid/regular/overtime hours, current estimated rates, costs, warnings and the exact provider material name/description/quantity/cost. The worker selection is separate from the Jobs screen's display filter.

The review refreshes when its job, dates, workers or parent dashboard revision change, when returning to the visible/focused tab, or through **Refresh job review**. It does not repeatedly download the full job catalog on a timer. Approve/send always rebuild and validate current server data, so a page left open cannot approve or dispatch a stale snapshot.

The job-cost policy is `proportional-day-lunch-chronological-week-overtime-v2`. Preserve original source/allocation hours. Apportion each qualifying worker-day's net paid hundredths across all positive source intervals using largest remainders, including shop, excluded and pending time; original break rows are comparison evidence and are not deducted twice. Order paid intervals by work date and clock boundaries, then assign regular/overtime hours using the saved weekly threshold. Apportion the existing weekly regular and overtime pay cents separately using largest remainders. Every worker-day paid total and each known weekly component reconciles exactly to the existing pay estimator. No blended hourly rate or source-cost substitution is used.

Supercrew exports clocks to minute precision. A positive interval of at most 0.02 hours with equal displayed start/end minutes retains its source quantity and a rounding warning. Such point intervals sort before a following longer interval at the same minute, with source-row/ID tie ordering. They do not invent clock durations or overlap a neighboring span merely by sharing its boundary; an interior overlap, missing/reverse clocks or a longer same-minute interval still blocks approval. Cross-approval same-worker/minute point reservations remain conservative duplicate guards. Zero-hour rows remain original evidence and do not become payable or approved intervals.

Incomplete weeks can display provisional estimates but cannot be approved for cost export. Selected workers require complete source weeks, known rates and unambiguous same-day clocks without overlaps throughout their contributing weeks. Allocation uncertainty elsewhere does not itself erase or exclude that source time from lunch/overtime calculations. Unknown rate or clock problems are explained in the review. Narrow the period or explicitly select other workers instead of guessing missing facts.

**Approve hours** stores the server-rebuilt snapshot, reviewed workers/dates, manager/time, full cost-relevant worker-week context and exact prepared provider request with hashes. It makes no provider calls. Changed quantities, relevant non-job time, allocation, rates, overtime policy or destination invalidate an unsent approval. **Review this approval** restores its dates/workers; the current review must match its hash before a separate confirmation enables **Send approved hours**. Concurrent revision checks and overlapping source-clock reservations prevent duplicate approvals/sends even after re-imported IDs or job remaps. Unsent stale/revoked reservations can be released through audited manager actions; dispatched/sent intervals cannot be silently released or sent again.

The user selected **Job Inputs**, preferring Miscellaneous if supported and otherwise Materials, with estimated labor costs. The [official Housecall OpenAPI](https://stoplight.io/api/v1/projects/housecallpro/housecall-public-api/nodes/reference/housecall.v1.yaml?fromExportButton=true&snapshotType=http_service&deref=optimizedBundle), verified October 13, exposes material inputs but no miscellaneous-category field or native employee labor-hour/timesheet endpoint. Send therefore appends **one normal Materials labor-cost summary per approved job/period** using `PUT /jobs/{job_id}/job_input_materials/bulk_update`. Quantity is **1**, unit cost is the exact approved total cents, and the name/description retain paid hours, original gross hours, regular/overtime hours, worker totals and snapshot reference. This avoids rounding a blended unit rate. It does not alter invoice services, customer prices, payroll or native Housecall time entries.

Keep the server-only `LABOR_HOUSECALL_SEND_ENABLED=0` (also disabled when omitted). Existing receipt export settings do not enable labor sends. A later explicitly authorized activation requires `LABOR_HOUSECALL_SEND_ENABLED=1`, all-job read access, a configured provider key and successful production acceptance. There is no labor-send cron or import-triggered dispatch; each send requires its own manager request and exact current approval. Do not approve or send real business hours as a development test. Do not transfer DEV approval/attempt records as production approvals.

Before each write, reconcile the frozen stable material reference and recheck the exact job/customer through the existing adapter. Durable dispatch authorization rechecks the current source revision, actor and lease after database lock waits. A timeout, crash or ambiguous response after entering dispatch stays **reconciliation required**; verification issues GET reads only. An absent readback never authorizes another PUT. Successful sends retain the provider material ID and immutable history. Reference conflicts or source changes after a send need manual correction review rather than automatic replacement. Proven pre-dispatch failures can be retried only with a fresh review and explicit send confirmation.

The approval migration was applied to DEV only after a fresh full migration replay, rollback SQL suites and separate-connection concurrency/expiry tests. The new tables were empty after installation; existing ledger revision, source imports and mappings were preserved. Browser/API/domain/provider tests use synthetic data or fake transports. No live labor write has been used for acceptance; that remains separately authorized work.

Parsed snapshots are rebuildable from private originals. Shared persistence stores import records separately and sends changed records with a manifest; ordinary heartbeats must not repeatedly rewrite all historical workbooks. Superseded parsed source records can be pruned while preserving original bytes, import hashes, summaries, and audit. Do not manually delete active source records or originals to reclaim space.
