# Labor Hours and Jobs production runbook

This is the October 13, 2026 integration runbook. It describes rollout and acceptance work; production is untouched by this integration work. Development has separate verification data; production still requires the reviewed rollout below. The development history remains in [labor-development.md](labor-development.md). Labor allocation is a reviewable estimate; this release does not post labor hours or labor costs to Housecall. Job linking saves only internal receipt-app identities. The user requires separate approval before any future labor-hour posting; existing receipt approval/export behavior remains unchanged.

## Release gates and existing accounts

The production pages and APIs require `LABOR_ENABLED=1`. Keep that flag off until the database migrations, source-file transfer, access checks, and worker acceptance pass. Production always uses Supabase persistence; a missing database is an error rather than a local-file fallback. A preview should use its own development database, credentials, worker token, and session key.

Reuse the receipt application's existing Supabase Auth users and profile roles. Do not copy users, passwords, or sessions from the local preview. Existing active managers/admins access Labor Hours and Jobs through the same login and authorization as the receipt inbox. Workers remain in the field app; anonymous, worker, and disabled accounts must fail the labor manager checks. Original-workbook downloads use authorized application endpoints. The private workbook and encrypted worker-session buckets are not public or available through ordinary authenticated Storage access.

`LABOR_LOCAL_PREVIEW=1` is only an explicitly enabled loopback development preview with filesystem persistence. It must remain off in preview/production. Browser mutations require the application's existing same-origin or authenticated request checks. Worker endpoints have a separate server-only token and narrowly scoped lease/session contracts; they do not grant manager access or receipt approval.

## Database and private originals

Commit and apply all four repository migrations in this order:

1. `supabase/migrations/20261013180457_labor_shared_persistence.sql`: shared state, per-import source records, immutable control-change audit, private original/session buckets, compare-and-swap updates, and all-bucket Storage monitoring.
2. `supabase/migrations/20261013182239_labor_worker_session_lease_fence.sql`: prevents an expired worker lease from replacing the encrypted session after a newer connection.
3. `supabase/migrations/20261013183059_labor_worker_session_expiry_after_locks.sql`: checks natural lease expiry after acquiring both the labor-control and session locks, so lock waits cannot extend authorization for a stale session write.
4. `supabase/migrations/20261013184807_labor_import_commit_lease_fence.sql`: validates the worker lease, command and import period at the atomic import commit after acquiring the shared ledger row lock, so a lease that expires during a lock wait cannot activate imported reports.

Apply and test these first on a disposable local or development database with the complete prior migration history. `npm run db:reset` rebuilds the selected local database and is suitable only for that disposable test environment. Run `npm run test:applied` for the repository's applied SQL acceptance. Verify manager read policies, denial for nonstaff/disabled users, immutable audit events, private Storage, stale revision rejection, and stale worker lease/session rejection. Take a database backup and verify the intended production project before applying the reviewed migration files there.

DEV migrations applied through the Supabase MCP may have remote version timestamps different from these repository filenames. Before a future `db push`, link this checkout to the **intended development project**, run `supabase migration list --linked`, and compare the actual applied SQL/function definitions with all four files. Repair migration **metadata only** after verifying equivalence: mark duplicate MCP-history versions `reverted`, then mark the corresponding repository versions `applied`, using `supabase migration repair VERSION --status reverted --linked` and `supabase migration repair VERSION --status applied --linked`. Substitute only the versions verified for that linked project; do not execute placeholder commands or remove unrelated migration history. Re-list the history and review `supabase db push --dry-run` before pushing anything. Metadata repair neither applies nor rolls back the SQL; it prevents already applied SQL from being pushed again under different filenames. See [Supabase migration repair](https://supabase.com/docs/reference/cli/supabase-migration-repair). Do not mark these versions applied on production before their SQL is reviewed and actually applied there. A backup, target-project check and reviewed production rollout remain required.

Production app server configuration uses its existing Supabase public URL/anon key and server-only service-role key, `LABOR_ENABLED=1`, `LABOR_LOCAL_PREVIEW=0`, and the private worker configuration below. `LABOR_PERSISTENCE=supabase` also allows testing shared persistence in a development runtime. Do not point a local preview or development seed script at production by changing an unrelated environment file.

The HTTP importer accepts at most **2 MiB (2,097,152 bytes) per XLSX** and **4 MiB (4,194,304 bytes) for the entire multipart request**, including multipart overhead. Two maximum-size files therefore do not fit in one request. Both Content-Length and streaming body bytes are bounded before multipart parsing; paired imports still require both reports. The worker download guard, structured parser and private original bucket have a separate 10 MiB file ceiling, which does not increase the HTTP import allowance. Split acquisition into smaller permitted date ranges when necessary; do not raise limits in deployment configuration without reviewing memory and host request capacity.

The checked seed is the private development ledger plus **nine** original XLSX files: five Timesheet imports and four Notes imports. The October 13 preflight recomputed SHA-256 for all nine original files and matched every stored import hash. Their combined original-file size is **457,587 bytes**. Keep the detailed manifest outside Git; its private local review artifact is `/private/tmp/svl-labor-original-manifest-2026-10-13.json`.

Use the guarded `initializeSharedLaborLedger(input, originals, actorId)` helper through a controlled server-side migration operation against an empty shared ledger. Supply the real active manager/admin's user ID and a map of only the nine referenced original IDs to bytes. The helper verifies hashes and source generation ordering, stores private originals, initializes the shared state with revision checks, clears local receipt fixtures and worker leases, and leaves downloads paused and disconnected. It rejects an already populated shared ledger. Seed development first and compare the resulting application data before repeating the reviewed operation on production.

Verify the seed by downloading every original through the authorized manager route and comparing SHA-256 to the private manifest. Import history must retain all five Timesheets and four Notes files. The winning complete Timesheet snapshots yield **1,259 current source entries**; overlapping import history must not duplicate their hours. Compare original clocks, quantities, source costs, owner/date note joins, source reconciliation warnings, allocation classifications, and original-download provenance. Nine files are import history, not nine additive payroll batches.

Retain the private reviewed allocation settings and user-approved worker rates exactly as saved. Missing rates remain unspecified, and inactive roster status does not erase historical hours. Weekly overtime uses the saved threshold, multiplier and starting weekday. These settings apply as estimates to the imported source history; they do not replace original source costs or payroll records. Daily lunch is calculated on complete worker days and remains separate from customer-job hours. Compare rules/pay revisions and the full settings privately during seeding rather than publishing employee rates or source identities.

Parsed snapshots are rebuildable from private originals. Shared persistence stores import records separately and sends changed records with a manifest; ordinary heartbeats must not repeatedly rewrite all historical workbooks. Superseded parsed source records can be pruned while preserving original bytes, import hashes, summaries, and audit. Do not manually delete active source records or originals to reclaim space.

## Housecall review before enabling links

The October 13 read-only review checked the complete 997-job catalog against the winning imported source data. Thirteen reviewed customer source locations are present, with zero exact full-customer/full-address automatic matches. Eleven locations have review candidates and two lack a candidate from the current catalog; six unclassified source locations remain pending. Classification and provider identity are separate decisions.

The private matching evidence is `/private/tmp/svl-labor-job-mapping-review-2026-10-13.json` with a Markdown table beside it. Review it before deployment or confirming any IDs. Some source properties have house-number/street discrepancies, and several customers have multiple provider jobs. Property-only, surname/entity token, and project-label suggestions are explicitly review evidence, not automatically confirmed links. Public examples must use synthetic identities such as `TEST Customer` and `TEST Job 1001`; real customer names, addresses, employee identities and rates belong only in private review data.

The manager editor shows the raw source address next to each candidate's full Housecall address, customer, number, status and ID. A new link needs an explicit manager confirmation, complete catalog fingerprint, and imported date range. Strong unique exact full-customer/full-address matches may use the exact-match action after server proof. Partial or changed catalogs, stale/unavailable rows, missing customer identity and conflicting mapping revisions cannot approve a new link. Existing historical mappings remain displayable if their catalog row later becomes unavailable. Removing a mapping is allowed even while the catalog is unavailable.

Date scopes do not carry forward automatically to future imports. Different ranges for the same source can link to different jobs; overlapping ranges are rejected. Preserve `sourceJobKey`, the resolved `destinationSourceKey`, allocation reason, note IDs and confirmation provenance. An A=B comment correction links the resolved B destination, not A's original source identity. Multiple source destinations mapped to the same Housecall ID must consolidate into one job with each allocated interval counted once and workers unioned once. Receipts join by that exact ID, using only their own assigned line amounts. Receipt-only jobs and unassigned receipt portions remain visible.

## Managed worker and normal Supercrew sign-in

Use the existing `.github/workflows/supercrew-labor.yml` finite workflow. It checks for due/requested work hourly. An idle check uses Node built-ins without installing browser dependencies. A claimed run installs pinned worker dependencies and Chromium, imports the paired reports, and clears private temporary files. Global workflow concurrency plus the database lease prevents overlapping import runs. The user's existing schedule is paused until setup and acceptance succeed.

Configure repository variables `LABOR_APP_URL` and `LABOR_APP_HOST` for the exact HTTPS application origin and hostname. Configure repository secrets `LABOR_WORKER_TOKEN` (at least 32 private random characters) and `LABOR_SESSION_ENCRYPTION_KEY` (a private 32-byte key encoded as 64 hex characters). The app server and setup operation need the same worker token; the session encryption key stays in trusted setup/worker environments. Keep values out of logs, Git, URLs, screenshots and client bundles. Normal report downloads use `SUPERCREW_REPORT_DOWNLOADS_APPROVED=1` only within the already approved source-export scope.

An operator completes **normal Supercrew login** in a private isolated browser through:

```sh
npm ci --prefix scripts/supercrew-worker --ignore-scripts
cd scripts/supercrew-worker
npx --no-install playwright install chromium
cd ../..
node --env-file=/absolute/private/worker-production.env scripts/supercrew-worker/hosted.mjs --connect
```

The private environment file must contain the exact hosted app origin/allowlisted host, worker token, encryption key and approved-download flag. Verify the Supercrew company before accepting the connection. The setup verifies a portable fresh browser session and uploads only encrypted authentication state; it downloads no reports. Do not transfer an entire Chrome profile, ask for passwords in chat, commit cookie files, or bootstrap a hosted worker from unrelated sessions.

The isolated connection setup succeeded against DEV and stored the encrypted Supercrew session there. Fresh Linux worker validation and a complete live paired report import remain pending. This development connection is not a live production worker and does not satisfy production acceptance.

The production **Request worker sign-in** control requests reconnection; the operator must still run the isolated connection setup and complete login. **Queue download** queues the configured paired export. The next hosted worker check claims it; an optional narrow workflow dispatch integration can wake the finite worker sooner. Configure the app server’s `LABOR_GITHUB_DISPATCH_TOKEN` with access limited to Actions on the intended repository, `LABOR_GITHUB_REPOSITORY=owner/repository`, and `LABOR_GITHUB_REF` for the reviewed deployed branch. Keep the dispatch credential separate from a developer’s personal login; the finite workflow still uses its own token and lease to import. Do not promise immediate download if dispatch is not configured. Inspect import history and last successful import before retrying an uncertain run.

The worker validates the expected company, all-job/all-worker Timesheet scope, Daily Timesheet Note scope, exact completed-date range and both XLSX structures before either report becomes active. Session expiry changes the status to sign-in required; a failed or interrupted lease must not silently mark success or repeat the same export. Reconnect normally when needed. Resume the daily schedule only after one complete live paired import and duplicate/retry verification succeed in the intended environment.

## Capacity and release acceptance

The current Supabase Free allowances are **500 MB database size per project** and **1 GB object Storage per organization**. These are distinct limits; workbook/session objects share Storage allowance with receipts, email originals and other project buckets. The all-bucket monitor now includes labor objects while preserving its confirmed-receipt metrics. See [Supabase billing quotas](https://supabase.com/docs/guides/platform/billing-on-supabase) and [Storage pricing](https://supabase.com/docs/guides/storage/pricing), verified October 13, 2026. Account count alone does not establish remaining capacity.

Before rollout, record actual database size, all-bucket Storage bytes and remaining organization allowance. Repeat after seeding and the first worker import. Do not infer database consumption from the 457,587 original-file bytes; parsed rows, indexes and immutable control audit occupy database space. Watch growth under recurring imports and confirm retention behavior before promising long-term fit on Free.

Acceptance requires the disabled feature to stay unavailable, an active manager/admin to load the enabled feature, a worker/anonymous/disabled account to be denied, original downloads to require access, and receipt approval/export behavior to remain intact. Inspect the actual production-mode UI for neutral copy, source/provenance details, unknown/pending hours, missing rates, incomplete weeks, scoped Housecall choices and receipt splits.
